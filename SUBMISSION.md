## Assumptions

1. **No real GPS hardware available.**
   The system simulates live GPS using a background script (tick.py) that
   inserts one coordinate per vehicle every 5 seconds along pre-defined
   NCR routes. In production this would be replaced by a TCP ingest
   service reading from real devices.

2. **Single depot per user.**
   Each driver and depot manager belongs to exactly one depot. The system
   does not handle transfers or temporary assignments across depots.

3. **One duty per driver per day.**
   A driver can only be assigned one duty on any given date. The backend
   enforces this with a conflict check before inserting.

4. **Driver app is a mobile-responsive web page.**
   Rather than a separate React Native app, the driver interface is a
   PWA-ready responsive route at /driver within the same React application.
   This is sufficient for a demo and matches the PRD recommendation.

5. **Seeded dummy data only.**
   All data — depots, vehicles, drivers, routes, duties, incidents,
   notices — is generated by a seed script on first startup. No real
   operational data is used.

6. **UTC timestamps stored, IST displayed.**
   All timestamps are stored in UTC in the database and converted to
   IST (Asia/Kolkata) when displayed in the frontend.

7. **Photo upload on incidents not implemented.**
   The database column (photo_path) exists and is ready. The frontend
   form and backend file handler were not completed within the submission
   window.

## Key Architectural Decisions

### 1. Monolithic backend over microservices
A single FastAPI application handles all four modules. This is the
correct choice for a demo-scale system — it is simpler to develop,
debug, and deploy. The code is organised into separate router files
(auth, avls, scheduling, ims, cms) so the module boundaries are clean
and the system could be split into microservices later if needed.

### 2. Polling over WebSockets for live map
The live map polls GET /api/v1/avls/live every 5 seconds. WebSockets
would reduce latency and unnecessary requests in production, but polling
is simpler to implement and completely sufficient for 6 demo vehicles.
WebSocket support is noted as a stretch goal.

### 3. JWT authentication with role-based access control
Every API route uses FastAPI's dependency injection to verify the JWT
token before the endpoint runs. Five roles are implemented — driver,
conductor, depot_manager, control_operator, admin. Depot managers and
drivers are scoped to their own depot at the query level.

### 4. State machine for incident management
Incidents follow a strict one-way workflow —
Open → Acknowledged → In Progress → Resolved → Closed.
Implemented as a Python dictionary mapping each status to its only valid
next status. Every transition is recorded as an incident_event row
creating a full audit trail.

### 5. Idempotent read receipts
The mark-as-read endpoint checks for an existing notice_read row before
inserting. Calling it multiple times has the same effect as calling it
once. This prevents duplicate receipts from network retries.

### 6. Docker Compose for one-command startup
All four services — database, backend, GPS simulator, frontend — are
defined in docker-compose.yml. The seed script runs automatically on
startup. A fresh clone runs with a single command and no manual setup.

### 7. GPS simulation design
tick.py reads vehicle IDs from the database on every tick rather than
caching them at startup. This prevents a race condition where the seed
script deletes and recreates vehicles while tick.py holds stale IDs.

## What Production Would Look Like Differently

| Area | Demo | Production |
|------|------|------------|
| GPS ingest | tick.py script | TCP ingest service + message queue |
| Live updates | Polling every 5s | WebSockets |
| Auth tokens | Long-lived JWT | Short-lived + refresh tokens |
| Database | Single instance | Managed RDS with replicas |
| Deployment | Docker Compose | Kubernetes or ECS |
| GPS pings table | No special indexing | Composite index on (vehicle_id, ts DESC) |
| Secrets | docker-compose.yml env vars | Secrets manager |

## Module Summary

**AVLS** — Live map with per-vehicle markers updating every 5 seconds.
Depot filter, click-to-inspect side panel, 30-minute polyline, full day
history view.

**Scheduling** — Route creation, duty assignment with conflict detection,
publish workflow, driver acknowledgement with timestamp.

**IMS** — Incident lifecycle from raise to close with mandatory notes at
each step, full audit timeline, driver panic button, severity-based
display.

**CMS** — Notice publishing with audience targeting, driver read receipts,
admin visibility into who has and has not read each notice.
